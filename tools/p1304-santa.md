# P1304 — permanent Christmas Santa gift

## Implemented

Item3 is a real account-owned Santa hat, separate from the existing random-colour
party crown2. One headwear slot; the aura1 is independent. Owner confirmed earned
Santa hats must remain after Christmas. The original low-poly bent red cap,
white brim and pompom are generated by `tools/santa_hat.py`, using the existing
static IQM writer. No third-party Santa mesh. Actual asset:864 vertices,288
triangles,31344 IQM bytes, one fixed palette. Native model draw, no shadow;
precache/entity setup at client initialization/map load, not first equip. Missing
assets skip cleanly. Other players, local body and the profile preview share the
same head/crouch attachment. Both inventory grids have a third item cell.

`SURFD_CHRISTMAS_EVENT=1` explicitly enables earning. Default is0/OFF. A linked,
not-banned account must have a current authenticated session in a trusted lobby's
roster. Web/profile/inventory reads, unlinked users, stale/cross-lobby tokens and
forged requests cannot earn it. No client grant operation. Actual event dates
are still an operator decision; this patch does not start Christmas early.
Earning never auto-equips. Event end never deletes ownership. A permanent2026
claim marker makes repeated polls/reconnects idempotent. Operator revoke keeps
the marker and does not auto-refill; an explicit operator grant can restore it.

## Preservation / compatibility

Core `PRAGMA user_version`, `SCHEMA_VERSION` and the newer-core guard remain26.
Three additive tables have their own component version1. Creation+stamp are one
transaction. Incomplete/unversioned/unknown versions or missing required columns
REFUSE instead of recreating ownership. No deployed database was ever schema27;
the failed pre-deployment prototype and correction are retained in task evidence.

The actual pre-patch inventory reader is frozen as a test fixture. It opens the
unchanged core26 DB and ignores, rather than deleting, the event rows. A rollback
can select the party crown without knowing Santa. Read-only views stay coherent;
the next modern authenticated inventory activity honours that later party choice
by changing only Santa equipment and revision, not ownership/earn/revoke markers.
At the revision ceiling the coherent view remains read-only; no overflow write.

Existing roster `inventory:1` remains, with optional `inventory_version:2` for new
servers. Older SSQC gets only its supported1/2 IDs; new SSQC gets all3. The private
equip/get form similarly opts in with `inventory_version=2`. Old clients retain
their9-field command. New clients negotiate11 fields using the EXISTING equip
command's non-equip `cap 2` shape only after their first verified private state.
Old servers silently ignore that shape. Public `*kit` appends a fourth Santa
flag; its first3 fields remain unchanged. None of this is a gameplay privilege,
client identity claim, arbitrary model path or recorder/evidence format change.
